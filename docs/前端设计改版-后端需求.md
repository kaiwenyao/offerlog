# 前端「Industry / 蓝图」改版 —— 后端需求清单

来源：Claude Design 画布 `OfferLog.dc.html`（设计系统 `industry-3d6501ff`）。
本轮**只改了前端**（视觉语言 + 少量结构），下面列出画布里有、而现有后端接口还撑不起来的能力。
每条给出：画布依据 → 现状 → 建议接口/表结构 → 前端会怎么用 → 优先级。

> 约定：所有路径省略 `/api/v1` 前缀；写操作沿用现有会话 Cookie + `X-CSRF-Token` 机制。

## 1. 工序线的节点日期（列表批量取阶段历史）

**画布依据**：数据库页「工序线」视图和详情抽屉的「工序进度」，每个阶段方块下方带一个日期
（`hist[]`）；已终止的岗位用灰色画到它真正走到的那一格。

**现状**：`application_events` 表已经存了完整的 `from_status / to_status / occurred_at`，
但只有单条查询接口 `GET /applications/:id/events`。列表页一次要渲染 60 行，
不可能发 60 个请求，所以前端现在**只能画到当前状态**：终止类状态（`rejected` /
`withdrawn` / `closed`）不在主流程枚举里，取不到它停在哪一格，整条工序线只好留空
（见 `frontend/src/components/StageTrail.tsx` 的 `railIndex`，返回 `-1` 时全部画空心格）。

**建议**：给列表响应加一个紧凑的阶段历史字段。二选一：

- **A（推荐，省一次往返）**：`POST /views/query` 与 `GET /applications` 支持
  `include=stage_history`，行对象里多一个：

  ```json
  "stage_history": {
    "saved":        "2026-08-14",
    "applied":      "2026-08-18",
    "screening":    "2026-08-25",
    "interviewing": "2026-09-02"
  }
  ```

  只取每个 `to_status` **最早一次**到达的日期（用户时区的日历日，`YYYY-MM-DD`），
  修正事件（`event_type = 'correction'`）按修正后的结果算。

- **B**：新增 `POST /applications/stage-history`，body `{ "ids": [1,2,3] }`，
  返回 `{ "items": { "1": {...}, "2": {...} } }`，上限 200 个 id。

**前端用法**：`StageRail` / `StageTrail` 直接把 `stage_history` 当 `path` 用，
终止岗位也能画出灰色的真实进度，方块 `title` 里显示日期。

**优先级**：**高**——这是画布与当前实现差距最明显的一处。

## 2. 命令面板（⌘K）的跨实体搜索

**画布依据**：顶栏那条「搜岗位、跳转、推进阶段… ⌘K」的命令条，弹出面板里混排
`岗位 / 跳转 / 命令` 三类结果。

**现状**：⌘K 只是把焦点丢给顶栏输入框，回车跳到 `/database?q=`。没有搜索接口，
面板本身没做。

**建议**：`GET /search?q=<kw>&limit=20`

```json
{
  "items": [
    { "kind": "application", "id": 13, "label": "字节跳动 · 前端工程师", "hint": "面试中 · 上海" },
    { "kind": "company",     "id": 7,  "label": "字节跳动",              "hint": "3 个岗位" },
    { "kind": "file",        "id": "uuid", "label": "简历_前端_v7.pdf",  "hint": "412 KB" }
  ]
}
```

- 匹配范围：`companies.name`、`applications.position`、`applications.notes`、`files.original_name`。
- 只返回当前 owner 的数据；空 `q` 返回最近打开的若干条。
- 建议 `pg_trgm` 索引，或直接 `ILIKE '%kw%'` 起步（数据量小）。

「跳转」和「推进阶段」这类命令由前端本地生成，不需要后端参与。

**优先级**：中。

## 3. 「记一个岗位」的 JD 链接预填

**画布依据**：新增岗位弹窗第一行「JD 链接或截图」，文案写明
「粘贴 JD 链接即可预填公司、岗位与城市」。

**现状**：弹窗只有公司 / 岗位 / 链接三个手填字段，`job_url` 存下来但不解析。

**建议**：`POST /applications/parse-url`，body `{ "url": "https://..." }`

```json
{ "company_name": "字节跳动", "position": "前端工程师", "location": "上海", "confidence": 0.8 }
```

**注意事项（后端实现时必须处理）**：

- 这是服务端发起的出站请求，属于 **SSRF 面**。必须限制协议为 `http/https`、
  解析后拒绝内网/回环/链路本地地址、禁止跟随跳转到内网、设超时和响应体大小上限。
- 建议加白名单域名或速率限制（每用户每分钟 N 次）。
- 解析失败要返回 200 + 空字段而不是 5xx，前端退回手填即可。

截图 OCR 预填（画布里的「或 ⌘V 粘贴截图」）建议**先不做**，成本远高于收益。

**优先级**：低（可选）。

## 4. 截图字段：附件挂到面试轮次

**画布依据**：
- 设置页「岗位字段」区块把「截图」标为本次新增的字段类型：*多图、可粘贴、按轮次归档*。
- 详情抽屉「截图与附件」区块：`⌘V 直接粘贴截图，自动挂到当前轮次`。

**现状**：
- `property_definitions.data_type` 枚举是 `text | number | select | multi_select | date | checkbox | url`，
  没有图片/附件类型。
- `application_files` 只有 `(application_id, file_id)`，**没有 `interview_id`**，
  附件挂不到具体轮次。
- 文件上传是 `POST /files`（multipart，可带 `application_id` 表单字段），
  前端可以从粘贴板拿到 `File` 对象直接传，这一半不需要后端改。
- 目前没有 `GET /applications/:id/files`：前端拉全量 `GET /files` 再按
  `application_id` 在客户端过滤。文件多了会浪费带宽，可以顺手加个查询参数。

**建议**：

1. `application_files` 增加可空外键：

   ```sql
   ALTER TABLE application_files ADD COLUMN interview_id BIGINT REFERENCES interviews(id) ON DELETE SET NULL;
   CREATE INDEX app_files_interview_idx ON application_files(interview_id) WHERE interview_id IS NOT NULL;
   ```

2. `POST /files` 的表单再接受一个可选 `interview_id`；同时给
   `GET /files` 加 `?application_id=` 过滤，返回里带上 `interview_id`，
   前端就能按轮次分组渲染，也不用再拉全量。
3. `property_definitions.data_type` 增加 `image`，`custom_values` 里存文件 id 数组
   （值本身还是 JSONB，不用改列）。删除文件时要同步清理引用它的 `custom_values`。

**优先级**：中（第 1、2 条）／低（第 3 条）。

## 5. 面试轮次的三态展示

**画布依据**：抽屉「面试轮次」列表右侧的状态标签：`已通过 / 待进行 / 待安排`。

**现状**：`interviews.result` 是 `pending / passed / failed`，配合 `scheduled_at` 是否为空，
前端其实**可以自己推**出三态（`scheduled_at IS NULL` → 待安排；`pending` 且有时间 → 待进行；
`passed` → 已通过）。当前前端已按这个规则渲染。

**建议**：不需要改后端。仅在将来要区分「已取消」与「改期」时，再考虑给 `result`
加 `cancelled` 值——注意日历接口已经有取消轮次的概念，改动前先对齐两处口径。

**优先级**：无（记录在此避免重复讨论）。

## 6. 本地开发：Vite 代理下写操作被 Origin 校验拦掉

**这不是设计改版引入的问题，但改版期间被反复撞到，一并记录。**

`backend/internal/platform/httpx/middleware.go:96` 的 CSRF 中间件会对
非 GET 请求做 `sameOrigin(origin, r)` 校验。通过 `npm run dev`（:5173）访问时，
Vite 代理只改 Host、不改 `Origin`，于是所有写请求返回
`403 {"code":"forbidden","message":"Origin 校验失败"}`，
前端在 dev 模式下**完全无法做写操作验证**（本次只能改用 `make up` 跑容器验证）。

**建议**（任选其一，都不弱化生产环境的防护）：

- 后端：读一个 `DEV_ALLOWED_ORIGINS` 环境变量，仅在该变量非空时把其中的 origin
  视为同源；生产不设置该变量，行为不变。
- 或前端：给 `vite.config.ts` 的 `/api` 代理加 `configure`，转发时把
  `Origin` 改写成 target 的 origin。（改前端更省事，但会让 dev 与生产的请求头不一致。）

**优先级**：中——影响日常开发效率。
