# 投递热力图方案

日期：2026-10-09  
范围：产品与技术方案，尚未实现。

## 1. 结论

在分析页加一块类似 GitHub 贡献图的「投递热力图」：横向按周排列，纵向是一周 7 天，每格一天，颜色深浅表示当天投递了多少个岗位。默认显示最近一年，可以切换到某个自然年。

- **数据**：后端新增 `GET /api/v1/analytics/heatmap`，按用户时区把 `applications.submitted_at` 按天分组计数，只返回有投递的日期。
- **渲染**：前端用项目里已有的 echarts（`calendar` 坐标系 + `heatmap` 系列）画图，不需要新增依赖。
- **位置**：分析页，放在指标卡和桑基图之间。

## 2. 口径（先定清楚，避免和其他数字打架）

| 问题 | 决定 | 理由 |
| --- | --- | --- |
| 「投递日」取哪个字段 | `applications.submitted_at` | 迁移 00006 以后它是派生列，取的是时间线上第一个「已投递」落点，已经考虑了更正和用户节点，不需要另外再查 `application_stage_points`。 |
| 按哪个时区切天 | 用户偏好时区（`users.timezone`），经 `timeutil.SafeLocation` 校验 | 和首页周条（`home/repo.go` 用 `submitted_at AT TIME ZONE $tz`）保持一致。晚上 23:30 在上海的投递必须算当天，不能按 UTC 算到前一天。 |
| 已删除（回收站） | 不计 | 用户已经不认这条记录。 |
| 已归档 | **计入** | 热力图记录的是「哪天做了什么」，归档只表示不想再看到，不会改变那天确实投过。**这一点和「已投递」指标卡（不含归档）不同**，图下方要写明。 |
| 内推 / 猎头等没有 `submitted_at` 的记录 | 不计入格子，单独显示「另有 N 条没有投递日期」 | 这些记录没有日期，没法放进某一天，但也不能悄悄漏掉。 |
| 筛选条件 | v1 不接分析页的渠道 / 标签筛选 | 分析页目前 summary 也没传筛选（`{}`）；之后要加筛选时，复用 `whereClause` 的写法即可。 |

## 3. 后端

### 3.1 接口

```
GET /api/v1/analytics/heatmap?from=2025-10-10&to=2026-10-09
```

- `from` / `to` 都是 date-only（`YYYY-MM-DD`，按 `platform/day` 的约定），闭区间，指用户时区下的日期。
- 两个参数都可以不传，默认是「用户时区的今天」往前 364 天，正好凑满 53 列。
- 校验：`from <= to`，跨度不超过 366 天，不满足就返回 400。

响应：

```json
{
  "timezone": "Asia/Shanghai",
  "from": "2025-10-10",
  "to": "2026-10-09",
  "today": "2026-10-09",
  "days": [
    { "date": "2026-09-30", "count": 4 },
    { "date": "2026-10-02", "count": 1 }
  ],
  "total": 5,
  "undated": 3,
  "years": [2025, 2026]
}
```

- `days` 只返回有投递的日期；补零、计算连续天数都交给前端（纯函数，好测）。
- `today` 由服务端按用户时区算好，前端算「当前连续投递天数」时用它，不依赖浏览器时区。
- `undated` 统计没有 `submitted_at` 但已经进入流程的记录，判断条件复用 `toApplyFactSQL` 取反后再加 `submitted_at IS NULL`。
- `years` 是有投递记录的年份，供年份切换器使用，避免用户点开空年份。

### 3.2 SQL

```sql
-- $1 owner, $2 tz, $3 from (date), $4 to (date)
SELECT (submitted_at AT TIME ZONE $2)::date AS d, count(*)
FROM applications
WHERE owner_id = $1
  AND deleted_at IS NULL
  AND submitted_at IS NOT NULL
  AND submitted_at >= ($3::date::timestamp AT TIME ZONE $2)
  AND submitted_at <  (($4::date + 1)::timestamp AT TIME ZONE $2)
GROUP BY d
ORDER BY d;
```

范围条件写成作用在 `submitted_at` 本身的区间（不写 `(... AT TIME ZONE)::date BETWEEN`），这样以后加索引时能用上。注意要用 `date::timestamp AT TIME ZONE tz` 做单次转换，原因见 `calendar/repo.go:176` 的注释。

单个用户的数据量在几百到几千条，`owner_id` 上已有的索引就够用，**不需要新迁移**。

### 3.3 代码落点

- `backend/internal/analytics/heatmap.go`：`func (r *Repo) Heatmap(ctx, ownerID, tz, from, to) (*Heatmap, error)`，附带 `Years` 和 `Undated` 两个小查询。
- `backend/internal/analytics/transport/http.go`：`Routes` 里加 `g.GET("/heatmap", h.heatmap)`。参数解析用 `day.Parse`，默认值按 `timeutil.SafeLocation(user.Timezone)` 算出的今天来定。
- `api/openapi.yaml`：补上 `/analytics/heatmap` 的定义。

## 4. 前端

### 4.1 组件

新建 `frontend/src/features/analytics/HeatmapPanel.tsx`，放在 `AnalyticsPage` 的 `MetricGrid` 和 `SankeyPanel` 之间。

```
┌ 投递热力图 ─────────────────── [最近一年 ▾] ┐
│ 最近一年投递 128 个 · 活跃 41 天 · 单日最多 9 · 当前连续 3 天 │
│ ▢▢▣▢▢▣▣ ... (53 × 7)                                          │
│ 少 ▢▣▣▣▣ 多          另有 3 条没有投递日期 · 已归档也计入     │
└───────────────────────────────────────────────────────────────┘
```

- echarts 配置：
  - `calendar.range = [from, to]`，`cellSize = ['auto', 14]`；
  - `dayLabel.firstDay = useWeekStart()`，和设置页的「每周起始日」一致；
  - `dayLabel` / `monthLabel` 用中文：`nameMap: 'ZH'`（或者自己传 `['日','一',…]`）。
- 颜色：`visualMap` 用 `type: 'piecewise'`，分 5 档：`0 / 1 / 2–3 / 4–6 / 7+`。档位按单日投递量固定，不根据 max 动态调整，这样不同年份之间可以直接比较。颜色直接用 `tokens.css` 里已有的 `--accent-200 / 400 / 600 / 800` 四档色阶（0 用 `--surface-hover` 一类的空格色），通过页面里已有的 `resolve()` 转成 canvas 能用的实际色值，暗色模式下自动跟随主题。
- tooltip：`10月9日 周五 · 投递 3 个`。为 0 的格子显示「没有投递」。
- 年份切换：「最近一年」加上 `years` 里的各个年份。切到某一年时，`from/to = YYYY-01-01 / YYYY-12-31`。
- 加载、失败、空状态沿用 `SankeyPanel` 的写法（转圈遮罩、失败时给文案和重试按钮）。如果一年里一次投递都没有，就显示「这段时间还没有投递记录」，不画一整块空网格。
- 窄屏：图表外层容器设 `overflow-x: auto`，画布保持最小宽度，大约 53 × 14px 加上标签宽度。滚动条初始滚到最右边，让「今天」直接可见。

### 4.2 纯函数（`frontend/src/features/analytics/heatmap.ts`）

- `fillDays(days, from, to)`：补成连续的 `[date, count][]`，供 echarts 使用。
- `heatmapStats(days, today)`：返回 `{ total, activeDays, maxDay, currentStreak, longestStreak }`。当前连续天数的规则：今天没有投递时，从昨天开始往前数（今天还没过完，不算断）。
- 日期一律按 `YYYY-MM-DD` 字符串运算，不经过 `Date` 的本地时区，避免出现差一天的问题。

### 4.3 类型与查询

- `lib/types.ts` 加 `HeatmapData`。
- `useQuery({ queryKey: ['analytics', 'heatmap', range], ... })`。目前前端没有任何地方 invalidate `['analytics']`，分析页靠重新挂载时重新请求，热力图沿用这个行为即可，不需要额外处理。

## 5. 二期（不在 v1）

1. **点格子下钻**：点击某天，跳转到数据库页并带上「投递时间 = 该日」的筛选。`views/filter.go` 已经有 `submitted_at` 的日期字段，还需要确认数据库页能不能从 URL 接收筛选；如果不能，就在热力图下方展开一个当天的岗位小列表。
2. **首页迷你版**：在 Today 页放最近 12 周的小图，作为每天的激励。
3. **按渠道 / 标签筛选**：接上分析页未来的全局筛选。
4. **叠加回复 / 面试**：切换「投递 / 收到回复 / 面试」三种事件，可以复用同一个接口，加一个 `kind` 参数即可。

## 6. 测试

后端集成测试（`backend/tests/integration/analytics_heatmap_test.go`）：

- 时区边界：用户时区是 `Asia/Shanghai`，`submitted_at = 2026-10-08T16:30Z`，应计入 `2026-10-09`；同一时刻对 `America/Los_Angeles` 用户应计入 `2026-10-08`。
- 删除的记录不计，归档的记录计入。
- `submitted_at` 为空但已进入流程的记录计入 `undated`，还在待投递的不计入。
- 更正：投递时间被更正之后，计数跟着新日期走（依赖 `submitted_at` 的回放，测的是端到端结果）。
- 参数：`from > to`、跨度超过 366 天、日期格式错误时都返回 400；不传参数时默认是 365 天的窗口。
- 越权：只统计自己的数据。

前端单测（`frontend/tests/heatmap.test.ts`）：

- `fillDays` 的首尾和闰年（2028-02-29）处理。
- `heatmapStats`：今天为 0 时连续天数不算断；有空档时最长连续天数的计算；空数据。
